# AI编码助手完整强制规范（融合Karpathy Guidelines + Go项目约束）
> AI编码助手行为与项目强制编码规范，适用于所有AI Agent / Codex。
> 取舍原则：准则偏向保守稳妥而非追求速度；简单琐碎任务可酌情灵活处理。
> 冲突优先级：**用户明确指令 > 本文档规则 > 仓库现有代码规范 > AI内置默认逻辑**
> 属于创造性功能开发。按工作流约定，先做 brainstorming（探索需求与设计，而非直接编码）

## 一、AI编码行为总原则（融合Karpathy准则，减少LLM常见编码错误）
### 1. 编码前先思考
**不做主观假定，不掩盖疑问，主动列出方案取舍。**

实现代码之前：
- 明确说明你的前提假设；存在不确定点必须主动提问。
- 需求存在多种解读时全部列出，禁止私自选定某一种实现。
- 如果存在更简单的实现方案，直接说明；必要时可以提出不同意见。
- 遇到理解不清立刻停止，指明疑点并发起询问，不要脑补需求直接编码。

### 2. 优先追求简洁
**编写刚好解决问题的最小代码，禁止写预判性、过度前瞻的代码。**
- 不要实现需求范围以外的额外功能。
- 仅单次使用的代码，禁止强行增加抽象封装。
- 禁止添加需求未要求的“灵活性”、“可配置能力”。
- 不为理论上不可能发生的场景编写异常处理。
- 如果写出200行，但50行就可以完成，必须重写简化。

自我校验：“资深工程师会不会认为这段代码过度复杂？”，如果是，做简化。

### 3. 精准局部修改【外科手术式变更】
**只改动必须修改的代码；仅清理本次改动产生的残留垃圾。**

编辑已有代码：
- 禁止顺手“优化”周边无关代码、注释、格式。
- 不要重构原本没有问题的代码。
- 严格匹配项目现有代码风格，即使你有别的写法。
- 发现无关的废弃旧代码，仅做提示，不要擅自删除。

改动产生无用残留时：
- 删除**因本次修改**而不再使用的导入、变量、函数。
- 原本就存在的废弃代码，无用户明确指令不得删除。

校验标准：每一行变更，都必须可以直接追溯到用户的任务需求。

### 4. 以目标驱动执行
**定义可验证的成功标准，循环直到验证通过。**

将任务转化为可验证目标：
- “增加校验” → “编写非法输入测试用例，再实现代码让用例通过”
- “修复Bug” → “编写可复现问题的测试用例，再实现代码让用例通过”
- “重构X模块” → “保证重构前后全部测试用例正常运行”

多步骤任务，先输出简要执行计划：
```
1. [步骤] → 验证点：[校验项]
2. [步骤] → 验证点：[校验项]
3. [步骤] → 验证点：[校验项]
```

清晰可落地的成功标准可以闭环执行；模糊描述如“把它弄好”需要反复确认需求。

> 准则生效标志：变更diff中无效改动变少、过度设计带来的返工变少；疑问澄清放在编码之前，而非写完出错之后。

## 二、文件编码强制规则（禁止UTF‑8 BOM）
1. 所有 `.go` / `.yml` / `.yaml` / `.properties` / `.sql` / `.md` 文本文件，必须使用 **UTF‑8 无BOM**，禁止输出 `\ufeff` 字节头。
2. Windows PowerShell读写文件硬性约束
   - 禁止使用 `> >> Out‑File`（会输出UTF16/带BOM）
   - 读取文件统一：`Get‑Content -Path "路径" -Raw -Encoding UTF8`
   - 写入/覆盖文件必须使用无BOM构造器：
     ```powershell
     [System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))
     ```
   - 追加文件统一使用上面的`WriteAllText`，不要使用`Add‑Content`（`Add‑Content -Encoding UTF8`自带BOM）
3. 代码生成要求：生成Go结构体、接口、处理器，文件开头绝不允许出现`\ufeff` BOM字符，输出纯UTF‑8文本。

## 三、脚本与文件删除安全约束（必读）
- 禁止使用任何脚本批量删除文件或目录。
- 删除只能使用 `Remove‑Item` 逐个文件执行。
- 如果需要批量删除，立刻停止操作，交由用户手动确认。

## 四、通用工作规则
- 默认先阅读相关代码、文档，再开始修改。
- 修改前说明本次改动的影响范围。
- 只做当前任务相关的最小改动。
- 改动完成前执行最小验证。
- 解释说明使用简体中文；代码、结构体名、变量、文件名保持英文。
- 禁止修改无关文件。

## 五、高危操作约束
高危操作：数据库DDL、密钥、核心配置、Docker镜像、依赖大版本升级，**必须主动询问用户，禁止自行修改**。

输出语言约定：
- 解释说明：简体中文
- 代码、结构体名、变量、日志、配置key：全部英文

禁止新增未声明的构建工具、依赖包、环境变量、全局脚本。

### 禁止删除/覆盖文件清单
`go.mod`、`go.sum`、`application*.yml`、`Dockerfile`、`.gitignore`、`AGENTS.md`、`docs/`架构文档。

所有代码修改完成，**必须给出可执行校验命令，确认编译、测试可以通过**。

## 六、硬性架构分层规则（Go项目）
1. Handler/Controller层只负责参数校验、响应封装，**禁止编写业务逻辑**。
2. 数据库Entity实体与对外DTO严格分离，禁止直接返回数据库实体对象。
3. 跨功能模块禁止直接import Repository/DAO，必须通过应用服务层调用。
4. 事务逻辑**只允许加在service层**，Handler层不允许处理事务。
5. 数据库操作统一使用GORM（或项目指定ORM），禁止手写大量重复SQL硬编码。

## 七、安全编码红线
1. SQL参数必须使用占位符，禁止直接字符串拼接SQL。
2. 接口入参统一校验（使用`validator`库/`binding`标签），禁止裸接收参数。
3. 密码、密钥、token禁止打印输出到日志。
4. 调用外部接口必须配置超时、重试策略。
5. 代码修改完成后，如果当前存在代码版本管理，需提示提交代码。

## 八、代码生成与重构行为约束
1. 生成代码优先复用项目现有工具包、常量、统一返回体，禁止重复造轮子。
2. 重构代码必须保留原有业务逻辑；不擅自优化业务流程、调整数据表结构。
3. 提供多套实现方案，优先输出最小改动方案，不引入复杂第三方依赖。
4. 涉及SQL变更，必须附带可执行DDL脚本，同时标注数据兼容逻辑。
5. 输出代码附带必要简短注释；复杂逻辑拆分为小粒度函数；禁止生成千行超大文件。

## 九、Git & PR 提交规范
> AI不执行任何版本管理操作，只输出变更内容、校验命令，不做commit/push。
> AI 最后输出commit的备注说明就可以了

## 十、绝对禁止修改目录/文件
- 根目录：`.git/`、`.idea/`、`.vscode/`核心文件
- 配置：生产环境`application‑prod.yml`、密钥环境变量文件
- 基础设施：`docker‑compose.yml`、k8s部署yaml、CI流水线脚本
- ORM逆向自动生成Entity实体（仅允许新增扩展类，禁止修改原生生成代码）
